## 3. The machine you are measuring on — read this before trusting any number

| | |
|---|---|
| `costs` | 5,821,770 rows |
| `costs_rollup` | 74,267 rows |
| `resource_presence` | 2,796,895 rows |
| Database size | **12 GB** |
| `shared_buffers` | **8 GB** |
| Buffer hit ratio | **69%** |

**The database cannot fit in memory.** Every detail-table query re-reads from disk.
This is the single most important fact about local performance, and it is a property
of the box rather than a bug.

Consequences you will hit:

- The same test suite measured **193s** and **579s** on the same commit, hours apart.
- Page-load timings varied 6.0s → 9.3s → 20.9s → timeout across identical runs.
- **Endpoint benchmarks are far more reliable than browser page-load numbers.** Prefer
  hitting `/api/...` directly with repeats over driving the browser, when you want a
  number you can act on.
- Heavy probing (a full-table scan, a rebuild) evicts the cache and poisons everything
  measured for the next 10-20 minutes. If results suddenly worsen, suspect this first.

## 5. Architecture you need to know

**The app is vanilla ES modules, not React.** The only npm dependencies are
`playwright` and `axe-core`, both test-only. React advice does not apply.

**Three-layer read path.** The dashboard almost never reads `costs`:

- `costs` — 5.8M-row detail table, month-partitioned (`CLOUDLENS_PARTITION_COSTS=1`),
  11 GB in the August partition alone.
- `costs_rollup` (74,267 rows / 17 MB) — pre-aggregated money. 11-column grain.
- `resource_presence` (2.8M rows) — per-resource identity and billed money.

`Reader.agg` / `.res` / `.named` name the derived table **when it can answer that
connection exactly**, and `costs` otherwise. A converted currency or a filter outside
the grain puts a query back on the detail table — that is usually why something is
unexpectedly slow.

Each derived module works out which filters it can serve **from its own grain**
(`derived.filterable`). Do not reintroduce a shared answer: `presence` used to borrow
`rollup.serves_filters` and `e7a681f` is exactly the change that would have broken it.

**Derived rebuilds** go through `derived.rebuild` — staging-swap into an inactive side
then `CREATE OR REPLACE VIEW`. Full rebuild ~130s; windowed to the months an import
touched ~4.9s. `refresh_rollup(window=)` ignores the window after any failed rebuild.

**Snapshot cache** (`app/snapshot_cache.py`) — durable, keyed on principal + tenant +
scope + path + query + generation. Invalidated when `data_generation` advances.

## 6. The one item left open

`stash@{0}` — `app/env_tags.py`, a derived table resolving the environment tag once
per ingest instead of once per row per request. **The design is right; the cost is not.**
The full rebuild **exceeded 24 minutes** on this estate and was cancelled. Resolving the
tag once per row via an inner select instead of three times did not rescue it.

Two facts that will save you repeating work:

- A pure-SQL `pg_input_is_valid` replacement for the `try_cast_json` PL/pgSQL shim was
  measured and **rejected**: identical answers (0 disagreements over 441,393 rows) but
  **slower** — 71.6s vs 38.0s — because inlining defeats the common-subexpression
  folding the opaque function was getting.
- PostgreSQL already folds the four `TRY_CAST` calls: 4-parses-per-row is 170.9s and
  1-parse-per-row is 161.9s over a 2.33M-row window. The parse count is not the problem;
  the per-row PL/pgSQL call with an `EXCEPTION` block, marked `PARALLEL RESTRICTED`, is.

Likely next idea: resolve `env` during **ingest** (in `staging`, where rows are already
being touched once) rather than in a separate rebuild pass over all history.

## 7. Working agreements that produced good results

- **Measure before and after, on the same warm machine.** Several "obvious"
  optimisations were rejected by measurement this session, including one of mine.
- **A failing test may be the test, not the code — but check.** Three test changes this
  session were legitimate (the property had genuinely changed); the fourth attempt
  revealed a real bug in my design.
- **Prefer endpoint benchmarks to browser timings** on this box (§3).
- Temporary scripts are `tmp_*.py` / `tmp_*.mjs` at the repo root and are deleted after
  use. The repo has no `tmp` gitignore entry — do not commit them.
- Commit messages explain *why*, with the numbers that justified the change.
